## 4. 两种使用流程

### 4.1 录制完成后提交

勾选“录制完成后自动写实渲染”时，默认切换为当前网页视角、640×384、5 FPS、深度开启、Mask 关闭。仍允许在开始录制前调整录制设置。

```text
录制动作 → 停止并生成本地视频 → 选出 Depth 或 RGB MP4
→ /uploads/mp4 → /jobs → 查询进度 → 分块预览 / 完整视频下载
```

需要单视角；Depth 控制需勾选深度录制。RGB 转 Canny 提交 RGB 通道。取消或只生成部分图像时不会自动提交。点击“重新提交”会创建新任务，不能当作恢复原任务使用。

### 4.2 持续采集并推送

“开始流式渲染”独立于本地录制按钮，不需要先编码整段视频；使用当前选定的单视角和 Depth/Canny 模式。流式采样固定 5 FPS，不取决于普通录制帧率下拉框。

```text
检查后端支持 5 FPS → POST /streams（input_fps=5）
→ 当前视角 WebGL 捕获 → RGB24 → 9/12 帧块顺序发送
→ 后端持续返回分块 → 前端预览
→ 停止输入 → 送完尾帧 → finish → 下载完整视频
```

- 每帧 `640×384×3=737,280` 字节，`uint8`、RGB 顺序，无 MP4/PNG/NPY 文件头。
- 首块 9 帧，后续 12 帧，画面时长分别为 1.8 秒、2.4 秒；最后一个块可短于规定帧数。
- 5 FPS 原始像素目标带宽约 3.69 MB/s；慢浏览器、网络和背压会影响实际采样与生成速度。
- 待发队列最多 2 块；收到 429 时重发相同序号和内容。队列满、慢读回或网页隐藏时暂停仿真，避免已采集帧被静默丢弃。
- 点击停止时先等待正在进行的采集和发送，再发送短尾块和 finish；输入帧数上限采用后端返回的 `max_frames`，缺省 4800。
- 首块预览需要点击播放，后续按顺序播放；生成慢时会等待，不保证无缝或实时播放。

## 5. 本次 5 FPS 变更的精确位置

这部分是在此前流式改造上进一步调整的内容：

1. `dist/stream-capture.js`：新增 `const INPUT_FPS = 5`；采集间隔与慢读回背压阈值都使用 `1000 / INPUT_FPS`；创建会话传入 `inputFps: INPUT_FPS`。
2. `dist/backend-render.js`：开启自动渲染时默认录制帧率改为 `5`；流式创建请求携带 `input_fps`，默认值为 5；开始前检查健康响应中的帧率能力。
3. `dist/index.html`、`README.md`：明确标记 5 FPS 输入需要后端帧率适配。
4. `tests/backend-render.test.mjs`：验证默认 5 FPS、会话声明，以及旧后端被拦截。

普通 MP4 上传已经包含视频本身的 FPS，现有后端可按视频时间轴重采样。原始帧流没有自带时间戳/FPS 文件头，不能仅把前端采样调为 5 后仍让后端按 16 FPS 编码，否则播放会约加速 3.2 倍。

## 6. 后端需要配合的协议（尚未修改）

**本节是后续建议，不代表后端代码已经实现。** 用户已要求后端修改先说明，本次只保留前端更改。

建议健康响应包含：

```json
{
  "stream_input": true,
  "fps": 16,
  "supported_input_fps": [5, 16]
}
```

前端会使用 `supported_input_fps` 检查是否包含 5；没有该数组时，只有健康响应自身 `fps` 为 5 才视为兼容。

前端流式创建请求已经发送：

```json
{
  "control_kind": "depth",
  "variant": "bf16",
  "prompt": "",
  "input_fps": 5
}
```

后端需在 `server.py` 接收、校验并向工作进程传递输入帧率；`render.py` 需按 5 FPS 编码，或通过明确的重采样规则输出 16 FPS 并保持时长。推荐直接 5 FPS 输出，模型的 9/12 帧分块可保留。当前后端固定 16 FPS，因此前端会显示不支持 5 FPS 的提示，暂不建立流式会话。模型实际出片还需在兼容的 PPU/GPU 环境验证。

## 7. Node 代理和网页转发路径

浏览器接口前缀由 `resolveRenderApi(import.meta.url)` 得出：

| 脚本访问路径 | 渲染接口前缀 |
|---|---|
| `/backend-render.js` | `/api/render` |
| `/proxy/5175/backend-render.js` | `/proxy/5175/api/render` |
| `/user/demo/proxy/5175/backend-render.js` | `/user/demo/proxy/5175/api/render` |

平台外层代理须将此前缀转发给 Node；Node 再移除 `/api/render` 转发到 Krea。仅发布静态 `dist/` 文件时也要配置等价的接口代理。后端目标地址由 `KREA_BACKEND_URL` 配置，不接受浏览器任意指定目标地址。

返回 HTML 登录页、代理页面或文本 404 时，新提示会包含实际接口路径和 HTTP 状态，不再笼统显示“请通过 npm start 打开网页”。

## 8. 样式变化

新增渲染区域此前浅色背景与继承的浅色文字冲突，现已统一为深色面板；原生 select、option、textarea、按钮、占位文字及焦点边界都有明确配色。说明文字字号和明度提高，主按钮使用橙色强调。

静态颜色计算中，正文、说明、输入提示、下拉框、主按钮和链接均超过 4.5:1 对比度。渲染区域在桌面限制最大高度并允许内部滚动，移动端保留正常页面滚动。此记录不等价于真实浏览器截图验收。

```bash

# 浏览器或平台端口转发访问 5175 端口
```

```bash
node --check server.mjs
```

代理测试需要本机监听端口；受限沙箱内可能无法执行。新增测试不加载真实模型。最近一次 5 FPS 调整后的前端状态测试 6 项通过；此前代理和发送队列测试通过。原有抓取测试依赖 `Array.prototype.toReversed()`，当前 Node 18 无法直接运行，建议完整测试使用 Node 20 或更新版本。尚未完成真实浏览器及 PPU 端到端出片验收。

+export function proxyRender(req, res, target) {
+  const route = req.url.slice('/api/render'.length);

+    res.writeHead(status, { 'Content-Type': 'application/json; charset=utf-8' });

+    const base = new URL(target);

+  }
